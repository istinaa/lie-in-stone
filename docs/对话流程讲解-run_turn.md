## 0. 全景图

```
玩家点「发送」
  │
  ▼  DialogueBox._request()                         scripts/ui/DialogueBox.gd:458
  │    busy = true，锁住输入框
  │
  ▼  NpcBrain.run_turn(npc, turn, line, 地点, special)   scripts/npc/NpcBrain.gd:166
  │    ├─ build_system_prompt()   固定部分：人设 + 规则 + 输出格式     :10
  │    ├─ build_state_prompt()    动态部分：内幕、数值、台账、对话…    :29
  │    │
  │    ├─ 最多 2 次：LlmClient.chat()  →  parse_json_content()        LlmClient.gd:94 / :172
  │    │             →  DialogueRules.sanitize()   校验，非法值静默改掉   DialogueRules.gd:105
  │    │
  │    ├─ 代码覆盖：turn==0、出示线索、邀请                            NpcBrain.gd:199–225
  │    ├─ DialogueRules.apply()     写入数值、台账、坦白、动作、态度    DialogueRules.gd:153
  │    └─ 记录对话，返回 {ok, result, notes}
  │
  ▼  回到 _request()：显示台词、系统提示、推荐回复；失败就显示「重试」
```

**一句话概括**：模型一次性提议 13 个字段，代码逐个把关，然后由代码写进状态。

## 第 1 站：UI 怎么发起一轮（`DialogueBox.gd`）

| 行 | 做了什么 |
|---|---|
| 360–367 `_on_send` | 取输入框文字，截到 200 字（`MAX_INPUT_CHARS`），调用 `_request(turn + 1, line)` |
| 370–375 `_on_invite` | 同样走 `_request`，多传一个 `{"type": "invite"}` |
| 378–385 `_present` | 台词前面自动加「（拿出「xx」）」，传 `{"type": "present", "card": id}` |
| 458–461 | `busy = true` 并锁住输入框：等模型回复期间不能连发 |
| 465 | `await NpcBrain.run_turn(...)` |
| 470–479 | 失败时显示「这句话没有生效，状态没有改变」，把原话放回输入框，并显示重试按钮 |
| 480–481 | **成功之后**才执行 `turn = t` |
| 501 | 模型选了 `end_conversation`，或者已经到第 8 句，就结束谈话 |

要注意 `turn` 的含义：**本次谈话里玩家已经成功说了几句**。`turn == 0` 是 NPC 先开口的那一轮，这时玩家还没说话。失败的那句不算数，所以重试时用的还是同一个 `turn + 1`（448–455）。

## 第 2 站：`run_turn` 的骨架（`NpcBrain.gd:166–235`）

整个函数分成四段，先记住这个结构：

| 段 | 行 | 做什么 | 会不会改状态 |
|---|---|---|---|
| ① 拼消息 | 170–173 | 一条 system 消息加一条 user 消息，没有多轮历史，历史已经拼进 user 里 | 不会 |
| ② 调用和重试 | 177–196 | 最多试 2 次；两次都失败就直接 `return` | 不会 |
| ③ 代码覆盖 | 199–225 | 按 `turn==0`、`special` 改写模型的结果 | 自己找一找（见第 6 站） |
| ④ 写入 | 226–235 | `apply()`，记录 NPC 台词，设置 `met`、`talked_today` | 会 |

②里有三个细节：

- 178：`chat(messages, true, 1000, 0.8)`，依次是 JSON 模式、最多 1000 token、温度 0.8。
- 181–182：如果是 Key、余额、参数这类问题（`error_is_key_problem`），**不重试，直接放弃**，因为重试也没用。这和 text2sql 的 `llm.py`「只重试暂时性错误」是同一个原则。
- 184–193：JSON 解析失败，或者没有 `reply`，都算失败，进入下一次尝试。**重试时发的是完全相同的 messages**，换一次结果只能靠温度 0.8 带来的随机性。

## 第 3 站：提示词（`npc_system.txt` + `build_system_prompt` + `build_state_prompt`）

### 3.1 为什么分成 system 和 user 两部分

`build_system_prompt`（10–26）只填人设字段。**同一个 NPC 每一轮的 system 消息一字不差。**

原因在 11 行的注释里：便于服务端缓存。DeepSeek 会对相同的前缀做缓存（prefix caching），命中的部分更便宜、更快。`LlmClient.gd:156` 用 `prompt_cache_hit_tokens` 统计命中量，可以在 F1 面板里看到。

> 面试可以连起来讲：这就是 vLLM 的前缀缓存（Automatic Prefix Caching）在 API 层的体现。W3 压测的 E5 会亲手测它。

### 3.2 system 里写了什么（`npc_system.txt`）

| 行 | 内容 | 作用 |
|---|---|---|
| 1–12 | 世界观和人设占位符 | 角色扮演 |
| 15–16 | 不承认自己是 AI；把「忽略设定」当成勇者在胡言乱语 | **防提示注入**：不是靠过滤关键词，而是让模型把注入内容当剧情处理 |
| 17 | 只知道【你知道的内幕】 | 认知边界，要配合 user 部分只注入已知事实 |
| 20–23 | 先听懂再开口：是不是在回答你，「他」指谁 | 针对试玩中发现的指代错误 |
| 25–30 | 说话要像真人：80 字以内，禁止排比、说教 | 反 AI 腔。**现在只靠提示词约束，代码不检查**，W1 的审查器要补上这一块 |
| 32–51 | 13 个字段的 JSON 格式，`understanding` 必须写在最前面 | 结构化输出 |

**为什么 `understanding` 要写在 `reply` 前面**：模型是从左到右一个 token 一个 token 生成的，先写出来的内容会成为后面内容的条件。先写「他在回答我的问题，『他』指大祭司」，再写台词，台词就会基于这个理解。这是一种最轻量的「先思考再回答」。放在 `reply` 后面就没这个作用了，因为台词已经写完了。

### 3.3 user 里每轮拼了什么（`build_state_prompt`，29–121）

| 行 | 信息块 | 读的时候想一想 |
|---|---|---|
| 32 | 【当前时间】 | 为什么不放进 system？（参考 3.1） |
| 34–37 | 【你知道的内幕】 | 只来自 `n.known_facts`，**认知边界就是在这里实现的** |
| 39–43 | 【勇者可能透露的内幕】 | 玩家知道、而这个 NPC 不知道的事实，**带 ID** 列出，模型只能从中选 |
| 45–46 | 【你对勇者的当前看法】 | 数值加上态度阶段的文字说明 |
| 47–55 | 承诺、坦白、心里的盘算 | 来自 flags 和 `GoalSystem.npc_mind` |
| 57 | 【你记得的事】 | 夜间压缩后的摘要 |
| 59–73 | 亲口说过的话（最近 10 条）、听来的（最近 8 条）、已指出的矛盾（最近 3 条） | **谎言台账**。矛盾由模型来发现 |
| 75–77 | 疑云值、公共事件 | 全局状态 |
| 79–82 | 【可用动作】 | `allowed_actions(n)` 生成的白名单，**提示词里就只给这些** |
| 83–86 | 推荐回复里能不能出现「坦白」 | 防止玩家随手点到不可撤回的选项 |
| 88–101 | 【最近的对话】，最多 12 行，按天分隔 | `HISTORY_LINES = 12` |
| 103–119 | 本次谈话的说明，加上玩家这句话 | 见下面 |

103–119 最值得细看：

- `turn == 0`（104）：明确告诉模型「勇者还没说话，数值变化填 0」。
- 第 7、8 句（109–110）：提示模型收尾。
- 115–117：**如果上一句是 NPC 说的，就拼成「【你刚才说的】……【勇者接着对你说】……」**。显式拼出「问—答」对，是为了让模型知道玩家在回答它的问题。这就是简历上「显式拼接上一句—这一句问答对」那一条。

## 第 4 站：`LlmClient.chat`（`LlmClient.gd`）

| 行 | 做了什么 |
|---|---|
| 95–96 | 带 `--mock-llm` 启动时走假模型 |
| 109–110 | `response_format: json_object`，即 JSON 模式。DeepSeek 要求提示词里出现「json」这个词，所以 `npc_system.txt` 和 `build_state_prompt` 第 120 行都写了 |
| 128–148 | 把错误分成 timeout / network / key / balance / rate / bad_request / server 几类 |
| 153–156 | 累计 token 用量：prompt、completion、缓存命中 |
| 172–182 `parse_json_content` | 宽松解析：从第一个 `{` 截到最后一个 `}`，兼容模型套上 ```json 代码块的情况 |
| 191–237 `_mock_chat` | 假模型：**靠搜索「【勇者接着对你说】」「【勇者这一轮说的话】」这两个标记**找到玩家的话，再按关键词（「没有神力」「加入」……）生成固定格式的回复 |

> ⚠️ W1 必须注意：mock 依赖提示词里的标记字符串。如果改提示词时改了这两个标记，mock 就找不到玩家的话，autotest 会大面积失败。指南 Step 4.4 要求「让 mock 认识新步骤」，就是这个原因。

返回值统一是 `{ok, content, error_kind, message, usage}`。调用方不用关心底层是网络错误还是 HTTP 错误。

## 第 5 站：`sanitize`，代码怎么把关（`DialogueRules.gd:105–150`）

原则写在第 4 行：**LLM 只「演」和「提议」，一切写进存档的变化都经过这里。**

| 字段 | 校验方式 | 行 |
|---|---|---|
| `reply` | 为空就整轮作废（返回 `{}`），否则截到 400 字 | 107–111 |
| `emotion` | 不在 7 种表情里就改成 `neutral` | 112–113 |
| `action` | **不在 `allowed_actions(n)` 白名单里就改成 `none`** | 115–116 |
| 三个 delta | `clampi_delta`：限制在 ±15；**不是数字的一律当 0** | 101–102、117–119 |
| `player_claims` | 最多 3 条，每条 60 字 | 120–125 |
| `player_confessed` | `_truthy`：兼容 true、1、"true"、"是" | 89–98、126 |
| `player_revealed_facts` | **必须是玩家自己知道的事实 ID**（`player_known`），否则丢弃 | 127–132 |
| `noticed_contradiction` | 字符串 "null" 和空串都当没有 | 133–134 |
| `suggested_replies` | 策略必须合法、不能重复；不满足条件时去掉「坦白」；最多 3 条 | 135–149 |

这里的模式只有三种：**白名单、限幅、ID 匹配**。面试被问「怎么防止模型越权」时，就答这三种，再各举一行代码。

**静默修改**：上表里多数字段非法时都是悄悄改掉，不报错，`reply` 也不会重写。指南 Step 1 的问题 3 就从这里找。

## 第 6 站：代码覆盖（`NpcBrain.gd:199–225`）

`sanitize` 之后、`apply` 之前，代码还会按情况**直接改写**模型的结果：

- **`turn == 0`（199–208）**：开场白不算数，数值归零，声明清空，重大动作改成 `none`。提示词里也说了「填 0」（104 行），所以是两道保险。
- **出示线索（214–220）**：数值按数据表变化（`GoalSystem.apply_present`），模型给的数值作废。
- **邀请（221–225）**：能不能加入由 `GoalSystem.can_join` 决定，模型选的 `action` 作废。

看邀请这一段，要和第 3 站的 `special_prompt`（137–140）对照着读：

- **生成之前**，提示词已经告诉模型「【系统判定】你已经决定答应」或「你现在还不会答应」；
- **生成之后**，225 行再强制改一遍 `action`。

所以邀请时台词和结果永远一致：**先裁决，再表演**。

普通对话没有生成前的那一步。模型同时决定动作并写台词，之后 `sanitize` 可能把动作改掉，台词却已经写好了。**W1 改造就是要把邀请这套做法推广到每一轮**，这是面试时讲动机的最好素材。

## 第 7 站：`apply`，真正写状态的地方（`DialogueRules.gd:153–228`）

按执行顺序：

1. 157–159：三个数值加上 delta，再限制在合法范围。
2. 161–164：声明写进 `n.player_claims`（谎言台账），最多保留 30 条。夜里 `GossipSystem` 会把它们传给别的 NPC。
3. 166–169：发现了矛盾，就记下来，**怀疑值额外 +5**，并提示玩家。
4. 171–182：坦白。设置 `knows_truth`，NPC 学会两个关键事实，怀疑值直接变成 100；主动坦白（怀疑值 < 80 时）信任 +5。
5. 184–188：透露的内幕写进 `n.known_facts`。
6. 190–219：按 `action` 设置 flag（加入、承诺帮忙、告发、分享情报……）。
7. 221–226：**重新计算态度阶段**。注意它在数值变化之后，所以这一轮的数值会决定下一轮的白名单。
8. 227：`GoalSystem.check_all`，检查心结有没有解开，并发放奖励。

返回的 `notes` 是给玩家看的系统提示，带 ★、⚠、× 这些前缀，UI 按前缀上色（`DialogueBox.gd:489–497`）。

## 8. 读代码时发现的几个值得注意的地方

这些不是指南要求的内容，但面试和 W1 改造都用得上。

1. **重试不带失败原因**（177–194）：解析失败后原样重发。可以对比 text2sql 的修复循环，那里会把报错作为 `user` 消息追加进去。这里不这么做也说得通：JSON 格式错误大多是偶发的，重新采样一次就够了，而且不会让上下文变长。
2. **`understanding` 现在只用于显示**：它只在 F1 调试面板里出现（`DialogueBox.gd:303–305`），不参与任何规则判断。W1 的「理解步骤」会把它升级成一个真正被代码使用的结构化输出：`reference`、`is_answer` 等字段。
3. **矛盾是模型发现的，代码只负责传播和记账**：`noticed_contradiction` 由模型判断，代码只是记下来、怀疑值 +5。简历上写「交叉验证」时要讲准确：传播是代码做的，比对是模型做的。
4. **记忆压缩失败时会丢失旧对话**（`NpcBrain.gd:253–258`）：258 行不管请求成功与否都会执行截断。失败时旧对话被丢掉，又没有摘要，这就是注释里说的「退化为截断」。好处是不阻塞夜间流程，代价是信息丢失。可以想一想：有没有更好的做法？
5. **`preview_present` 的「快照 → 试算 → 恢复」**（145–163）：先保存 flags 和数值，改动后试算目标，再原样恢复。W1 Step 5.3 要做流水线的失败回滚，可以直接借鉴这个手法。

## 9. 自测题

先闭卷答，再看第 10 节的参考答案。这些题和指南的 5 个问题不重复，偏向「为什么」。

1. 为什么同一个 NPC 每轮的 system 消息要一字不差？如果把【当前时间】移进 system，会有什么后果？
2. `understanding` 为什么必须写在 `reply` 前面？放在 JSON 最后还有没有用？
3. 玩家点「邀请」，但 `can_join` 为 false。台词和最终的 `action` 怎么保证一致？两道保险分别在哪一行？
4. 模型返回 `"trust_delta": "20"`（字符串）会怎样？返回 `30` 呢？
5. 模型返回 `"player_confessed": "是"` 会怎样？为什么要专门写 `_truthy`？
6. 模型把某个事实 ID 填进了 `player_revealed_facts`，但玩家自己并不知道这件事，会怎样？这样设计是为了防什么？
7. 夜间压缩时 DeepSeek 正好挂了，会发生什么？你觉得这样设计好不好，有没有更好的办法？
8. 如果在 W1 把提示词里的「【勇者这一轮说的话】」改名为「【玩家发言】」，`--mock-llm --autotest` 会出什么问题？
9. 解析失败时，这里原样重试；text2sql 则把报错反馈给模型。两种做法各适合什么情况？

## 10. 参考答案

<details>
<summary>先自己答，再展开</summary>

1. 为了命中服务端的前缀缓存：相同的前缀不用重新计算，更便宜、首 token 更快。【当前时间】每个时段都会变，放进 system 会让前缀从这里开始就不一样，后面的人设和规则也全都缓存不上了。所以规律是：**不变的内容放前面，变化的内容放后面**。
2. 自回归生成时，先生成的 token 是后面 token 的条件，所以先写理解，台词就会基于这个理解来写。放在最后时台词已经写完了，`understanding` 只能起到事后解释的作用，帮不了台词，最多用来调试。
3. 第一道是生成前的提示词：`special_prompt` 的 140 行写了「【系统判定】你现在还不会答应……action 填 refuse」。第二道是生成后的代码：`run_turn` 的 225 行强制把 `action` 设为 `refuse` 或 `none`。前者保证台词是拒绝，后者保证状态不会被模型改成加入。
4. `"20"` 是字符串，`clampi_delta` 里 `v is int or v is float` 不成立，结果**当成 0**：数值不变，也不报错。`30` 会被限制到 `15`。可以想一想：字符串直接当 0 合理吗？更宽容的做法是先尝试 `to_int()`。
5. `_truthy` 会把 "是" 识别为 true，坦白生效。之所以专门写它，是因为模型的输出类型不稳定：可能是 true、1、"true"、"是"。而且 GDScript 里 int 和 bool 直接比较可能报错。
6. 会被丢弃（127–132 行只接受 `player_known` 里的 ID）。玩家不可能透露自己都不知道的事。这是为了防两件事：一是模型「脑补」玩家透露了内幕；二是玩家通过提示注入，让 NPC「学会」本不该知道的事实。认知边界因此由代码保证，而不是靠模型自觉。
7. 258 行照常执行截断：旧对话被丢掉，`memory_summary` 不更新，这部分记忆就永久丢失了，但夜间流程不会卡住。一种改进是：失败时不截断，保留原样，等下一晚再压缩。代价是这一天的上下文更长、token 更多。或者给压缩单独做一次重试。
8. `_mock_chat` 找不到标记，`line` 为空字符串。坦白、加入这些关键词全部匹配不上，依赖这些行为的测试项都会失败。这说明 mock 和提示词之间存在隐式耦合，改提示词时要同步改 mock，或者把标记抽成常量。
9. 格式类的偶发错误，比如 JSON 少了个括号，重新采样就能解决，原样重试简单而且上下文不变长。语义或执行类的错误，比如 SQL 列名写错，同样的输入很可能再犯一次，必须把错误信息告诉模型，它才知道改哪里。

</details>
